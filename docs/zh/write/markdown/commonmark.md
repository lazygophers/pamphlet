# Markdown 基础语法

这一页把**每一种基础语法逐个写全**：怎么写、出来是什么、有哪些坑。不需要先去别处补课。

底层用的是 CommonMark（Markdown 的标准化版本，规范在 <https://spec.commonmark.org/>）。Pamphlet 是它的**严格超集**：只新增语法，绝不改变既有语法的行为——所以你在别处写的 Markdown 拿过来就能用。

## 标题

一到六级，井号后面**必须有一个空格**：

```markdown
# 一级标题
## 二级标题
### 三级标题
#### 四级标题
##### 五级标题
###### 六级标题
```

七个井号不是标题，会当成普通文字。

### 一级标题是文档标题

文档里第一个 `#` 会成为产物的 `<title>`（浏览器标签页上显示的那行字），除非你在 frontmatter 里写了 `title`。

它也**不进目录**——目录是文档内部的导航，文档标题本身不是其中一节。

所以正文分节从 `##` 开始写，一份文档里 `#` 只写一个。

### 每个标题自动带锚点

标题会自动得到一个 id，可以直接深链过去（把网址末尾加上 `#` 和那个 id）。规则是：

| 标题写的 | 得到的锚点 |
|---|---|
| `## 提示块` | `#提示块` |
| `## Theme tokens` | `#theme-tokens` |
| `## 第 1 步：装一次` | `#第-1-步装一次` |

也就是：转小写、空格换成连字符、标点去掉、**中文原样保留**。两个标题重名时，第二个自动加 `-2`。

文档内部跳转就写 `[跳到提示块](#提示块)`。

### 目录收到第几级

目录默认收到二级，`toc.deep` 可以改到 1–6。设置写法见 [frontmatter 参考](/reference/frontmatter)。

## 段落与换行

**空行分段**。连着写的两行属于同一段，不会换行：

```markdown
这两行
在产物里是同一段。
```

真要在段内换行，行尾打**两个空格**，或者用一个反斜杠 `\`：

```markdown
第一行在这里断开··
第二行

第一行在这里断开\
第二行
```

（上面的 `··` 表示两个空格，实际写的时候是看不见的——所以反斜杠那种写法更可靠。）

## 强调与行内代码

```markdown
**粗体** 或 __粗体__
*斜体* 或 _斜体_
***又粗又斜***
`行内代码`
~~删除线~~
```

- 中文之间用 `**粗体**`（星号）比 `__粗体__`（下划线）稳妥：下划线形式要求两侧是空格或标点，夹在中文里可能不生效
- 行内代码里的内容**原样显示**，里面的星号、井号都不会被当成语法
- 行内代码里要写反引号时，外面用两个反引号包：`` `` 里面有 ` 反引号 `` ``
- 删除线是 GFM 扩展，见 [GFM 扩展](/write/markdown/gfm)

## 引用块

行首一个 `>`：

```markdown
> 引用的话写在这里。
>
> 空行也要带上 `>`，否则算两段。
```

引用块里可以继续写别的：列表、代码块、甚至再套一层引用（`>>`）。

**引用块的长相由主题决定**：多数主题是左边一条竖线，`architecture` 主题把它排成一条「决策记录」。

## 列表

### 无序列表

`-`、`*`、`+` 三个符号等价，**同一份文档里保持一致**就行：

```markdown
- 第一项
- 第二项
- 第三项
```

### 有序列表

```markdown
1. 第一步
2. 第二步
3. 第三步
```

**编号由浏览器算**，所以源文档里写 `1.` `1.` `1.` 也会正确渲染成 1、2、3。想从别的数字开始就把第一项写成那个数字（`3.` 开头则从 3 数起）。

### 嵌套

子项**缩进到与上一层文字对齐**——无序列表缩 2 个空格，有序列表缩 3 个：

```markdown
- 第一项
  - 子项
    - 孙项
- 第二项

1. 第一步
   1. 子步骤
   2. 子步骤
2. 第二步
```

### 一项里放多段、代码块、图片

同样按对齐缩进：

````markdown
1. **装一次**

   ```bash
   npm i -g @nekoleapuki/pamphlet-cli
   ```

2. **编译**

   得到 `方案.html`，双击打开。
````

### 紧凑与松散

列表项之间**有空行**时，每一项会被包成段落，行距变宽（术语叫「松散列表」）；没有空行就是紧凑的。想让列表看起来紧凑，项与项之间不要留空行。

### 任务列表

`- [x]` / `- [ ]` 是 GFM 扩展，见 [GFM 扩展](/write/markdown/gfm)。

## 代码块

### 围栏式（推荐）

三个反引号包住，开头那行写语言名就会按语言高亮：

````markdown
```typescript
const a = 1
```
````

不写语言名就是纯文本，不高亮。

**代码块里要放代码块时，外层用四个反引号**——外层的反引号个数必须比内层多：

`````markdown
````markdown
```bash
echo 甲
```
````
`````

### 缩进式

每行缩进 4 个空格也算代码块。它和列表的缩进容易打架，**建议一律用围栏式**。

### 图表围栏

围栏语言写 `mermaid` 时不再是代码，而是**一张编译时画好的图**，见[图表围栏](/write/diagrams/)。

## 链接

```markdown
[行内链接](https://example.com)
[带悬停提示的链接](https://example.com "鼠标停上去会显示这句")
<https://example.com>
[跳到本文档的某一节](#提示块)
```

最后一行是**站内锚点**，锚点规则见上面「每个标题自动带锚点」。

引用式写法适合同一个地址反复出现：

```markdown
详见[压测报告][报告]，另见[报告][报告]的第三节。

[报告]: https://example.com/report "3 月压测"
```

方括号里的名字**不区分大小写**，定义行写在文档任何位置都行，它本身不会出现在产物里。

## 图片

```markdown
![图片说明](./图/架构.png)
```

方括号里是替代文字（图加载不出来时显示它，屏幕阅读器也念它）。

**图片在编译时被内嵌进产物**，路径相对于源文档、远程地址直接报错、单张上限 2MB——完整规则见[图片与资源](/write/assets)。

## 分隔线

单独一行写三个或更多的 `-`、`*`、`_`：

```markdown
---
```

:::warning 文档开头的 `---` 是 frontmatter
源文档**最开头**那对 `---` 之间的内容是配置（frontmatter），不是分隔线。想在文档第一行放分隔线，改用 `***`。
:::

## 转义

想让 `*` `_` `#` `[` 这些符号显示成它本身，前面加一个反斜杠：

```markdown
\*这不是斜体\*
5 \* 3 = 15
```

## 表格

表格是 GFM 扩展，写法和对齐见 [GFM 扩展](/write/markdown/gfm)。

## 裸 HTML 原样通过

源文档里的 HTML **直接渲染成 HTML，编译器不做任何过滤**。`<style>` 标签、`style` 属性、内联 `<svg>` 全部原样进产物。

没有 `allow-html` 这个开关 —— 不是「默认关」，是**没有这个概念**。

安全上的唯一防线是产物里那份严格 CSP（内容安全策略：浏览器执行的一份「什么能跑、什么不能跑」的清单）。

### CSP 挡住了什么

以下全部实测过：

| 源文档里写的 | 产物里的结果 |
|---|---|
| `<script>alert(1)</script>` | 被拦 —— `script-src` 只允许运行时那一个哈希 |
| `<img onerror="...">` 等内联事件属性 | 被拦 —— 内联事件处理器需要 `'unsafe-inline'` |
| `<iframe src="https://...">` | 被拦 —— `default-src 'none'` |
| `<img src="https://...">` | 被拦 —— `img-src` 只允许 `data:` |
| `<form action="https://...">` | 表单可显示，提交去向被拦 |

### 没挡住的两样

这两条是**明知的、被接受的**设计后果，不是 bug。

**一、`<style>` 标签和 `style` 属性。** `style-src 'unsafe-inline'` 是那份 CSP 唯一的松口 —— 样式全部内联，没有别的写法。

因此**源文档里一段 `<style>` 可以盖掉整个主题系统**。

:::danger 最常见的来路是复制粘贴
从别处复制一段带 `style` 的 HTML 片段贴进文档，然后发现主题坏了 —— **这不是 bug，是设计**。
:::

想改样式的正确做法见[换一套主题色](/howto/theme)，不是往文档里塞 `<style>`。

**二、内联 `<svg>`。** 它绕过整条图表管线：

- 不经过 SVG 消毒 —— 可以带 `<animate>` 等 SMIL 标签，那正是消毒规则明确不放行的东西
- 不经过颜色替换 —— 切到深色模式时它不会跟着变

也就是说 **SVG 有两条待遇完全不同的路径**：引擎产出的 SVG 被严格消毒，作者手写的 SVG 完全不受约束。如果你基于「所有 SVG 都被消毒过」做了别的判断，会踩空。

### 为什么不过滤

考虑过三种更严的做法，全部落选：

- **剥掉 `<style>` / `style` 属性，把内联 `<svg>` 送进消毒和换色**：精确对应 CSP 挡不住的部分。落选。
- **整体走 DOMPurify 默认白名单**：不用自己设计规则，但默认名单随版本漂移，而且它**默认就放行 `style` 属性和 `<svg>`**，并不解决上面两个问题。落选。
- **原样通过但对 `style` 给警告**：保留作者控制权。落选。

选原样通过的收益是**行为最可预期**：作者写什么就是什么，等于 CommonMark 加一个 HTML 渲染器，零意外。这也让「兼容纯 Markdown」这条承诺没有任何例外。

如果日后要收紧，第一个该收的是 `style` 属性 —— 它的收益（保住主题系统）最大、对作者的损失最小。
