# 兼容性承诺：0.x 只承诺修订号兼容

| 升级 | 承诺 |
|---|---|
| `0.0.1 → 0.0.2` | **不破坏任何东西** |
| `0.0 → 0.1` | **允许破坏**语法、CLI 参数、AST、插件 API |

第一个发布的版本是 **0.0.1**。

这与[语义化版本对主版本号为零时的规定](https://semver.org/lang/zh-CN/#spec-item-4)一致，不是 Pamphlet 自创的规矩。

## 这对你意味着什么

**每次次版本升级（中间那位数字变了）都要检查自己的文档是否还能编译。**

```bash
pamphlet lint "docs/**/*.md"
```

放进 CI 里，升级时它会第一时间告诉你哪份文档编不动了。

代价是真实的：对早期采用者不友好。这个代价被接受了，换来的是**语法在 0.x 期间可以自由纠错**——包括删除和重命名已经发布的语法。

## 三样明确不稳定的东西

:::danger 别拿它们当稳定接口
- **AST 结构**（`pamphlet ast` 的输出）—— 0.x 期间不承诺兼容
- **CLI 参数** —— 次版本可以改名、可以删
- **插件 API** —— 同上
:::

这三样恰恰是早期最需要反复调整的部分。把它们在 0.1 就锁死（考虑过，落选）等于把最该改的地方焊死。

## `spec:` 字段现在只做一件事

```yaml
---
spec: 1
---
```

它的作用退回到**单一职责：标记「这是一本 pamphlet 的源文档」**。

它**不再**触发多套解析器行为——原始设计里那条「旧 spec 永久支持、解析器多版本共存」已经删除。只维护一套解析器，永久的双倍维护成本被消掉了，这是这个决定最大的实际收益。

`spec` 高于编译器支持的版本时报 `DOC-101`。不填等于不做检查。

## 1.0 会重新做这个决定

到那时应当给出比修订号兼容**强得多**的承诺。现在这条只适用于 0.x。
