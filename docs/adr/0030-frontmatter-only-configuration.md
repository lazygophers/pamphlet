# 没有配置文件，所有配置只走 frontmatter

不存在 `pamphlet.config.yaml`。所有配置写在源文档的 frontmatter 里，包括自定义引擎声明：

```yaml
---
title: 订单系统方案
theme: tech-dark
lang: zh-CN
toc:
  enable: true
  deep: 2
engines:
  graphviz:
    langs: [dot]
    command: [dot, -Tsvg]
---
```

CLI 参数可以覆盖 frontmatter。

## 为什么

范围声明：这个工具只针对**单一 md 文件**输出 HTML 做扩展优化，**不涉及整个文档集**。而「项目级配置文件」本身就预设了「一批文档共享一套设置」——那正是文档集的概念。

## Considered Options

- **保留配置文件只放自定义引擎声明**：引擎声明写一次、多份文档共用。落选——为一个字段保留整套机制（文件查找、解析、schema 校验、诊断码），而且「配置文件在哪、往上找几层」这些问题本身只有文档集工具才需要回答。
- **配置文件作为 frontmatter 的默认值来源**（原始设计的做法）：写一批风格统一的文档时最省事。落选——它把文档集这个概念保留在了产品里。

## Consequences

**连带删除四样东西**：`config` 包、配置文件的 schema 校验、`CFG-5xx` 这一整类诊断码、以及「配置与 frontmatter 谁优先」这条规则（没有第二方了，规则自动消失）。

**产物承诺更强**：一份 `.md` 完全自描述——发给谁、在哪台机器上编译，结果都一样。不存在「在我这儿好的，在你那儿编出来不一样」这类问题。

代价是用自定义引擎的人要在每份文档里重复写那段声明。这个代价只影响少数场景（内置的七个引擎不需要声明，见 [0008](./0008-builtin-engines.md)）。

如果日后重复声明真的成为负担，正确的解法是让 frontmatter 支持引用一个引擎声明文件（一个显式的相对路径），而不是把「自动查找项目配置」加回来——前者仍然是自描述的，后者不是。
