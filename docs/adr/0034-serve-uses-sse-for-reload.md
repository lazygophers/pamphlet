# `serve` 用 SSE 推送刷新，整页 reload

`pamphlet serve` 起一个本地 HTTP 服务，**在预览响应里**额外注入约十行脚本（正式产物一个字节都不受影响）。文件变化后重编译，通过 SSE（服务器推送事件，浏览器原生的 `EventSource`）推一条消息，脚本收到就 `location.reload()`。

## Considered Options

- **WebSocket**（用 `ws` 之类的库）：生态里最常见，将来若预览需要双向通信（例如浏览器把滚动位置报回来做「保持位置刷新」）已有通道。落选——引入一个依赖，而当前没有任何双向需求。
- **轮询**（预览页每 500 毫秒问一次）：实现最简单，任何 HTTP 服务都能做。落选——刷新有最多 500 毫秒延迟，而增量构建的目标本身就是 500 毫秒以内，轮询会把感知延迟拉到接近两倍。
- **不做自动刷新**：`serve` 只做静态服务。落选——写图表时改一根箭头要手动切窗口刷新，而那正是 `serve` 存在的理由。

## Consequences

SSE 是浏览器原生的，零依赖；单向推送正好够用（服务推、浏览器听），而 WebSocket 的双向能力在这里没有用途。

**整页刷新而不是热替换**：产物是单文件、重编译很快，整页刷新最简单也不会出现「状态残留」那类诡异问题。代价是刷新后 Tab 展开状态、滚动位置会丢——这个代价被接受，因为热替换要处理的边界情况远多于它节省的时间。

关键约束：**注入只发生在预览响应里**。正式产物必须与 `serve` 完全无关，否则「预览里好的、导出后坏了」就会成为可能——而那是这类工具最难查的一类问题。
