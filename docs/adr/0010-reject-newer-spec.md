# `spec:` 高于编译器支持版本时报错拒绝编译

`spec:` 声明的是**这份文档要求的最低编译器语法版本**。它高于当前编译器支持的版本时，报 `DOC-101` 并以退出码 1 结束，不产出任何 HTML。低于或等于自身版本的正常编译。

**`spec:` 不填等于不做检查**（视为「任意版本都行」），而不是视为 `spec: 1`。作者只有在用到了某个版本才引入的语法、且希望老编译器明确报错时，才需要写它。

这是 [0006](./0006-versioning-promise.md)（`0.1 → 0.2` 允许破坏语法）的必要配套：承诺了次版本可以破坏语法，就必须让破坏被看见。

## Considered Options

- **警告但继续编译**，未知语法按通用规则降级为普通段落：对使用者更宽容，至少能拿到产物。落选。
- **不检查 `spec:`**，完全依赖「未知语法降级为普通段落」这条通用规则：代码最少。落选。

两个落选项的问题是同一个：那条降级规则是为「拼错了指令名」设计的，用在版本不匹配上会让 0.2 的新语法被 0.1 悄悄降级成普通文字——**编译成功、产物看起来正常、内容其实是错的**。而这种产物会被直接发给客户。在「明确报错」和「静默产出错误内容」之间，编译器类工具必须选前者。

## Consequences

实现成本极低：一个数字比较加一条诊断。

因为 `spec:` 可以不填，它**不能兼任「这是一本 pamphlet 的源文档」的标记位**——[0002](./0002-source-extension-is-md.md) 里那个说法需要相应修正：要编译哪些文件完全由 CLI 参数或配置里的文件清单决定，源文档本身不带任何身份标记。

诊断文案必须给出出路，而不只是报告失败：错误消息里要同时写明文档需要的 spec 版本、当前编译器支持的版本、以及升级命令。
