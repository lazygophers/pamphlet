# 主题 token 分三层，元素层默认从语义层派生

主题变量分三层：

1. **语义层**（约 12 个）：`--pf-bg` / `--pf-bg-subtle` / `--pf-fg` / `--pf-fg-muted` / `--pf-primary` / `--pf-border` / `--pf-info` / `--pf-warn` / `--pf-danger` / `--pf-font-sans` / `--pf-font-mono` / `--pf-radius`。
2. **元素层**（30+ 个）：按具体元素分——表格边框、代码块背景、引用块左边框、每种 callout 各自的底色与图标色、以及图表专用的那组（[0016](./0016-diagram-theming-by-post-processing.md) 替换 SVG 颜色时指向这一层）。**默认值全部从语义层派生**：`--pf-table-border: var(--pf-border)`、`--pf-code-bg: var(--pf-bg-subtle)`、`--pf-callout-warn-bg: var(--pf-warn-subtle)`……
3. **作者层**：自定义主题只写想改的。改主色写一行；单独调表格边框也写一行，覆盖那一个元素 token。未写的从内置主题继承。

内置主题用同一套规则写，不给自己开后门。

## Considered Options

- **扁平一层，自定义主题必须写全 30+ 个**：规则最简单，任何值一眼可见。落选：改主色要手动改十几个值，而且极容易漏掉一个导致某处颜色不搭。
- **扁平一层但可只写部分、未写的继承内置主题**：比上一项友好。落选：仍然没有派生关系，`--pf-table-border` 不知道自己该跟着 `--pf-border` 变，所以「改主色」这个最常见的需求依然要改十几处。

## Consequences

细粒度的价值是「需要时能精确控制」，而不是「每次都必须精确控制」。派生让这两件事同时成立。

代价是一次性的设计工作：每个元素 token 都要想清楚它从哪个语义 token 派生。做完之后写在内置主题文件的注释里，那份注释就是主题系统的文档。

派生关系必须是**一层**的（元素层只能引用语义层，不能引用别的元素层），否则改一个语义 token 的影响范围会变得难以预测。
