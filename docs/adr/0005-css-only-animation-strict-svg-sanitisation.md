# 动效只用 CSS，SVG 消毒白名单不放行 SMIL

所有动效（滚动进入、逐步揭示、多帧切换）编译为 CSS 动画与 CSS 类切换，SVG 本身保持静态。SVG 消毒白名单保持严格：不通过 `ADD_TAGS` 放行 `<animate>` / `<set>` 等 SMIL 标签。多帧动画的实现方式是「输出多个静态 SVG 帧，用 CSS 控制显示哪一帧」。

## Considered Options

冲突的来源：原始设计一边要求把图编译成多帧 SVG 动画，一边要求所有 SVG 都过 DOMPurify 消毒。而 DOMPurify 的 SVG 白名单**默认就会移除** `<animate>` / `<set>` / `<discard>`，因为 SMIL 是已知的 XSS 攻击向量（<https://github.com/cure53/DOMPurify/issues/900>，另见 #1058、#236）。两条规则同时执行，等于动画被自己的安全策略删掉。

- **放行 SMIL（`ADD_TAGS`）**：SMIL 能做 CSS 做不到的事（沿路径运动、图形属性插值）。代价是亲手在自己的安全边界上撕开一个已知攻击面，而这个攻击面的输入是「图源」——一旦有人把 Pamphlet 用在处理不可信输入的场景（接受投稿、渲染他人提交的文档），这就是真实漏洞。
- **P0 不做动效**：最省事，但放弃了表达力目标里的动效部分。

## Consequences

这不是对安全的妥协换取功能，也不是对功能的妥协换取安全：原始设计自己写的原则就是「动效全部编译为 CSS/SVG 声明式实现」，本决定只是把这条原则执行到底，并明确它对消毒策略的含义。

附带收益：SMIL 的浏览器前景本身不确定（Chrome 曾宣布过弃用意向），赌 CSS 比赌 SMIL 稳。

约束：任何将来「这个动效只有 SMIL 能做」的需求，都要先回到这份 ADR 重新评估安全边界，不能就地 `ADD_TAGS`。
