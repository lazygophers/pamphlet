# 产物体积不设 CI 卡点，只输出归因报告

产物体积没有会让构建失败的阈值。`--verbose` 输出一份归因报告，说明体积花在哪（运行时、每张图的 SVG、每个内嵌资源）。原始设计里 NFR-2 那组「纯文本 ≤ 50KB / 含交互 ≤ 120KB / 含运行时图表 ≤ 1MB（CI 卡点）」不再作为硬性门槛，`size-limit` 那一层测试也随之取消。

## Considered Options

- **分档卡点**（无图 / 有图无位图 / 含位图 三档各一个阈值）：能让每类文档都被真正卡住。落选。
- **单一数字**（≤ 3MB 或 ≤ 5MB）：一条规则一个检查，但纯文字文档失去保护——运行时涨十倍也不触发报警。落选。

## Consequences

单个资源 2MB 的上限（见 [0005](./0005-css-only-animation-strict-svg-sanitisation.md) 之外的资源内嵌规则）仍然存在，所以体积不会无声无息地失控到任意大：它的增长被「每个资源 ≤ 2MB」和「作者自己放了几张图」限制着。

代价明确：体积回退没有自动保护，只能靠人看 `--verbose` 的报告。对一个把「自包含、随手可分发的小册子」当核心隐喻的项目，这是把判断权交给作者而不是编译器——如果将来发现产物普遍偏大，需要重开一份 ADR 把卡点加回来。

归因报告因此从「可有可无的调试功能」升级为体积治理的唯一手段，必须做得足够好读。定下来的形态：

```text
产物 docs/方案.html  1.2MB (gzip 380KB)  编译耗时 3.4s

  贡献            原始      gzip     占比
  ─────────────────────────────────────────
  内嵌图片 (3)    820KB    790KB    68%
    架构图.png    610KB    600KB
    截图-1.png    140KB    135KB
  字体子集         290KB    285KB    24%
  图表 SVG (5)      68KB     14KB     6%
  源文档内嵌        18KB      6KB     1%
  运行时 (4 特性)   12KB      4KB     1%

建议
  · 架构图.png 610KB —— 这是一张流程图，改用 ```d2 或 ```mermaid 可降到约 20KB 并支持主题联动
  · 字体子集 290KB —— 文档用到 1480 个不同汉字；若可接受系统字体，去掉 theme.font 可省 290KB
  · 截图-1.png 140KB —— 未经压缩的 PNG，试 `pngquant --quality=70`
```

三条要求：按贡献排序（第一眼就看到该动哪里）；**同时给原始与 gzip 后的大小**（gzip 后才是实际传输和感知的大小——图片和字体几乎不压缩，而 SVG 能从 68KB 压到 14KB，只看原始大小会误判优先级）；建议必须具体到可执行的命令或替代写法（「图片太大」不是建议，「改用 d2 可降到 20KB」才是）。
