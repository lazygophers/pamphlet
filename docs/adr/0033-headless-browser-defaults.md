# 无头浏览器：超时 10 秒，不做并发改成批量传入

Mermaid 预渲染（见 [0004](./0004-mermaid-via-headless-browser.md)）的两个默认值，都按实测定：

- **单批渲染超时 10 秒**。`--timeout` 可覆盖。
- **不做并发**。没有 `--concurrency` 参数；取而代之是「一次把这份文档里所有 Mermaid 图交给渲染器」。

超时后按 [0028](./0028-failed-diagram-produces-artifact-but-fails-build.md) 处理：报 `DIAG-303`、产出占位框、退出码 1。

## 实测依据

原先这份 ADR 定的是超时 30 秒、并发 CPU 核数减 2，并明确标了「两个数字都没有实测依据」。现在有了（macOS / Node 22）：

| 场景 | 实测 |
|---|---|
| `import mermaid-isomorphic` | 221ms |
| 第 1 张（**含浏览器冷启动**） | 733ms |
| 第 2 张起 | 364ms |
| 40 节点大图 | 412ms |
| **一次传 3 张（批量）** | **455ms** |

两处修正：

1. **30 秒失去依据。** 它建立在「无头浏览器冷启动是秒级」这个假设上，而实测最慢是 733ms。30 秒是实测最坏值的 40 倍以上，实际后果是一张图真的卡死时作者要干等 30 秒。10 秒 ≈ 最坏值的 13 倍，是超时值的常规定法（比观测最坏值大一个数量级）。
2. **并发这个概念不必要。** 批量 3 张 455ms，逐张是 3 × 364 = 1092ms——瓶颈不在并行度，而在每次调用的往返。一次传一批比开多个浏览器实例更快、更省内存，还少一个参数。

## Consequences

引擎接口因此定成「一次收一批」而不是「一次收一张」：`render(requests: RenderRequest[])`。

**超时只是不再等，并不能取消底层渲染**——无头浏览器那边还在跑。所以超时后必须把被抛下的那个 promise 的失败吞掉，否则它稍后失败会变成 unhandled rejection，在 `serve` 这种长期进程里会反复冒出来。这一点是写测试时撞出来的，已经在 `withTimeout` 里处理。

`--timeout` 保留，文档的 `serve` 一节应当提到「写图表时可以把它调小，换更快的失败反馈」。
