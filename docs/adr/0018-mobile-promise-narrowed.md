# 移动端承诺收窄为「打开之后的体验」，不承诺「怎么打开」

不为移动端改变产物形态。README 与文档站里写清限制与绕行方式：手机端请通过 iOS 的「文件」App 打开，或让发送者把产物放到任意网页服务器上。

原始设计的用户故事「我在手机微信里打开产物，希望 Tab 可点、图表缩放不糊、暗黑模式跟随系统」改写为：**在手机浏览器里打开时（无论来自本地文件还是网址），Tab 可点、图表清晰、跟随系统亮暗。**

## Considered Options

事实基础：**iOS 18.5 起 Safari 已不允许直接打开本地 HTML 文件**（<https://discussions.apple.com/thread/256102223>，Apple 社区多人复现；非官方文档）。微信内置浏览器默认阻止本地 HTML 直接执行（中文技术社区来源，非官方文档）。两件加起来，原来那个用户故事在 2026 年的 iOS 上大概率不成立。

- **为移动端多做一个可托管的多文件版本**（`--format hosted`）：落选，与「自包含单文件」的核心定位背道而驰，要维护第二条组装路径和第二套测试，而且仍然受制于同一个限制。
- **先不管，等有人抱怨**：落选。第一个在 iPhone 上打不开产物的人会认为这是 Pamphlet 的 bug，这种第一印象对开源项目伤害不小。

## Consequences

这是操作系统层面的限制，不是 Pamphlet 能解决的问题；任何试图绕过它的方案都会把复杂度引进产物却仍然受限。

收窄后的承诺是**完全成立**的：CSP、`location.hash` 深链、data URI 字体、`prefers-color-scheme` 都在 `file://` 下实测通过（见 [0017](./0017-strict-csp-in-artifact.md)）。留一个做不到的承诺比收窄承诺伤害更大。

文档站必须有「在手机上打开」这一节。这不是可选的文档润色——它是本决定的执行部分。

第一版 README 里不放这一节（第一版 README 只讲「这是什么、为什么值得用」，技术边界全部在文档站）。风险敞口要记清楚：README 是外部人的第一入口，撞上「手机打不开」时他们不一定会去文档站找答案。
