# 兼容性承诺：0.x 期间只承诺修订号兼容

0.x 期间只承诺修订号级别的兼容：`0.1.0 → 0.1.1` 不破坏任何东西，`0.1 → 0.2` 允许破坏语法、CLI 参数、AST 和插件 API。这与语义化版本对主版本号为零时的默认规定一致（<https://semver.org/lang/zh-CN/#spec-item-4>）。因此原始设计里那条「旧 spec 永久支持、解析器多版本共存」被删除：只维护一套解析器。

## Considered Options

- **分层承诺**（源文档语法在整个 0.x 内只增不减，CLI 与 AST 按 0.x 默认可变）：对使用者更友好，且「不删已发布语法」这条纪律不需要多套解析器。落选。
- **整个 0.x 内全部冻结**：把 AST、插件 API、CLI 参数在 0.1 就锁死，而这些恰是早期最需要反复调整的部分。落选。
- **只承诺修订号兼容**（采用）：等同语义化版本默认，社区无需额外解释即可理解。

## Consequences

代价明确：使用者每次次版本升级都要检查自己的文档是否还能编译。对一个以外部开发者采用为目标的开源项目，这会让早期采用者更倾向观望。这个代价被接受，换来的是语法在 0.x 期间可以自由纠错——包括删除和重命名已发布的语法。

「解析器多版本共存」被删除，意味着永久的双倍维护成本被消掉了，这是本决定最大的实际收益。

`spec:` frontmatter 字段保留，但它的作用退回到单一职责：标记「这是一本 pamphlet 的源文档」（见 [0002](./0002-source-extension-is-md.md)），不再触发多套解析器行为。

1.0 发布时需要重新做一次这个决定，届时应当给出比修订号兼容强得多的承诺。
